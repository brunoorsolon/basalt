# Redrock releases

Redrock is an independent engine distribution. Releases describe engine, adapter and platform contracts without depending on a particular installation manager or consumer.

## Meaning of stable

`vMAJOR.MINOR.PATCH` identifies an immutable Redrock release. Stable means a reviewed, tested baseline for the configuration declared in its release notes and manifest, not general AMD/Linux compatibility. Use a major version for incompatible supported engine/adapter or model-artifact contracts, a minor version for compatible capabilities or newly qualified configurations, and a patch version for compatible fixes. Upstream version numbers do not determine Redrock's version.

[The 1.0.0 baseline](releases/1.0.0.md) records the first accepted configuration. A release is published only when its tag and required assets exist; an accepted baseline or a successful build alone is not publication. Candidate builds remain unqualified until matched to retained qualification evidence.

## Cut a release

1. **Freeze the combination.** Start from the exact tested engine/adapter commit and dependency pins, not today's upstream heads. Record the tested executable/library digests, model/pack/MTP identities, launch settings, platform closure and evidence digests in `releases/<version>.json`. Keep raw logs, credentials, machine paths and consumer-specific evidence private; publish a sanitized result and content identities. Documentation-only release commits may follow the tested commit if `git diff <tested> <release> -- src include frontend cmake CMakeLists.txt tools third_party data .gitmodules` is empty; inspect any other build inputs too. Preserve the actual tested source identity rather than relabelling binaries as built at the later commit. **Done:** every claimed result binds to immutable inputs and any source difference is accounted for.
2. **Preserve repaired dependencies.** Include the upstream base, complete source patch or reachable pinned fork, resulting source-tree hash, license notices, build recipe, toolchain/input identities and tested output digests. Apply patches during explicit dependency source preparation, never during configure/build/startup. Record the complete required runtime closure, including dynamically loaded libraries and vendor data. Stock dependencies are not interchangeable with repaired ones. **Done:** another builder can reconstruct the tested sources and recipe without a private commit or a mutable branch.
3. **Qualify only affected scope.** Reuse adequate retained evidence for the unchanged tested combination. Changed engine/adapter/dependency/toolchain/kernel/model inputs or settings require the affected build, protocol, parity and attended hardware/model checks before extending support. Cover both MTP modes when both are claimed, authentication, useful long-context output, limits, fresh starts, cancellation, failure cleanup and resource/kernel observations. Keep independent review findings and accepted exceptions visible. **Done:** the supported matrix, failures, exceptions and remaining uncertainty are explicit; compilation and execution are separate evidence.
4. **Assemble without activation.** Keep engine, matching headless adapter and repaired ROCr together as one versioned combination, with licenses, manifests, build provenance and checksums. A source release must supply reconstruction inputs and recipes; a binary release must additionally supply the exact qualified payloads and required loader/platform contract. Models are identified, not bundled by default. Repackaging preserves file digests; relinking, RPATH rewriting or rebuilding produces a new candidate requiring affected checks. The current `tools/redrock.py build` packages only an engine, not the complete qualified combination. **Done:** payload checksums and licenses are verified and no installed/default runtime or rollback/model input has changed.
5. **Publish the frozen version.** After human acceptance of the release candidate, create an annotated `v<version>` tag at the reviewed release commit and publish release notes, manifests, reconstruction inputs and `SHA256SUMS`; include qualified binaries only if declaring a binary release. Verify the remote tag resolves to that commit and downloaded assets match their checksums. Tags and assets are immutable: correct mistakes in a new version, never retarget or replace a published baseline. **Done:** tag, commit, assets, checksums, support scope and limitations agree. If an input or publication step is missing, report the release as pending, not published.

## Updating after a release

Use [UPSTREAM.md](UPSTREAM.md#repeatable-update-procedure) for an update check or incorporation. An update check recommends bounded changes; it does not merge them, run GPU workloads, publish a release or activate an installation. Publication and activation are separate decisions. Consumers pin a Redrock tag **and resolved commit**, manifest and payload hashes, not moving upstream branches.

Keep prior releases, qualification evidence and rollback inputs intact. An accepted optimization is not part of a stable release until its candidate passes the affected gates and a new Redrock version is published.
